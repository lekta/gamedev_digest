- По диагонали: .NET — `Utf8Parser` для `int` самый медленный из целочисленных перегрузок, `TryParseInt32D` не проходит порог инлайнинга (31.10) — issue dotnet/runtime #136761 автора bgrainger (`author_association: CONTRIBUTOR`), прочитан своими руками через api.github.com. По моему чтению тела: `TryParseInt32D` остался полностью развёрнутым методом на 659 байт IL и не проходит порог профитабельности инлайнера, остальные `TryParse*D` инлайнятся; замеры на локальной сборке main для входа «0» — `out int` 2,18 нс, `out long` 1,24, `out uint` 1,19, `out short` 1,36, `out long` с сужением до int 1,41; на «42» — 2,37 против 1,37/1,41; на .NET 10.0.14 `out int` на «0» даёт 1,98 нс против 1,39 у сужаемого long. Предложение автора — реализовать `TryParseInt32D` через `TryParseInt64D` с проверкой диапазона (минус ~133 строки, плюс ~6), прототип: «0» 2,13 → 1,28 нс, «42» 2,39 → 1,53, «-7» 2,16 → 1,64, «12345» 3,34 → 2,86, «123456789» 4,21 → 4,03, «-2147483648» 4,60 → 4,71. Для 8/16-битных и `uint` автор того же не предлагает — они уже инлайнятся и через 64-битный путь станут медленнее. Связанный PR #136762 я НЕ открывал.
